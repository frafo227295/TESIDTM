\section[Backend Infrastructure]{Backend Infrastructure and Data Platform Architecture}

To operationalize the domain-oriented Data Product model and support interactive analytical workloads within Amadori S.p.A., 
the enterprise data architecture is undergoing an evolutionary transition from an on-premises relational infrastructure toward a scalable, cloud-native platform. 

The baseline enterprise environment relies primarily on an on-premises Oracle database, which has historically served as the operational transaction 
repository and the default target for analytical queries. To overcome the computational constraints of centralized on-premises hardware and eliminate 
contention between transactional processing and resource-intensive analytics, the target architecture introduces Google BigQuery as the enterprise cloud data warehouse. 
BigQuery provides a serverless, highly scalable environment based on distributed compute engines and columnar storage, enabling parallelized execution of complex 
analytical queries over large-scale historical datasets.

Rather than implementing an abrupt cutover, the transition follows a phased migration strategy. 
In the initial phase, analytical workloads and reporting pipelines continue to query the operational Oracle database directly. 
As data models, historical partitions, and ETL routines are progressively refactored and validated, tables are transferred to Google BigQuery. 
During this transitional period, both database environments remain active concurrently.

\section[The Semantic Layer with Looker and LookML]{Formalizing Business Data: The Semantic Layer with Looker and LookML}
\label{sec:looker_lookml}

To operationalize the conceptual definitions established by the enterprise ontology and provide an auditable single source of truth across analytical processes, 
the architecture implements Looker and its declarative modeling language, LookML. In this stack, Looker acts not merely as a visualization layer, 
but as the centralized execution engine for the enterprise Semantic Layer \cite{patel2023comparative}. 
Operating on an in-database query paradigm, the platform keeps analytical data within the underlying storage while dynamically compiling user requests, dashboards, 
and API calls into optimized SQL queries executed by the target engine at runtime \cite{gartner2021magic}.

This centralized abstraction plays a strategic role in the phased migration from the on-premises Oracle database to Google BigQuery. 
By isolating semantic definitions from physical database dialects, LookML allows metrics and dimensions to initially query Oracle instances and subsequently repoint 
to cloud tables as domain migrations conclude. Downstream analytical consumers, executive reports, and AI interfaces remain entirely insulated from storage shifts, 
experiencing continuous metric integrity and zero operational disruption.

For example, the operational material planning pipeline currently populates the core fact table (\texttt{F\_MATERIAL\_PLANNING}) via a daily batch job on Oracle. 
When this workload is migrated to BigQuery in a future deployment phase, only the model-level connection parameters and dialect syntax will require adjustment in LookML. 
The exposed business logic and entities will remain untouched, ensuring seamless continuity for downstream users and cognitive agents.

\subsection{Architectural Best Practices and Performance Optimization}
Designing a high-throughput Semantic Layer requires balancing analytical flexibility with computational efficiency. 
When modeling complex supply chain dynamics in LookML, several engineering best practices were applied to minimize query execution overhead and prevent maintenance 
bottlenecks \cite{googlecloudlookerbp2024}:
\begin{itemize}
    \item \textbf{Pushing transformations upstream:} Complex business logic, recursive allocations, and historical rolling aggregations are executed upstream 
    during database batch processing rather than calculated dynamically inside LookML. 
    Looker is dedicated strictly to dimensional aggregation, filtering, and metric definition, eliminating resource-intensive row-level computations at query runtime.
    \item \textbf{Denormalization of frequently filtered attributes:} While relational normalization minimizes redundancy in transactional (OLTP) systems, 
    analytical workloads benefit from dimensional flattening. Frequently joined descriptive attributes are pre-aggregated or denormalized into wide structures, 
    reducing join depth across large-scale fact tables.
    \item \textbf{Handling surrogate keys and natural identifiers:} Technical surrogate keys used internally for database joins are systematically hidden from 
    end users (\texttt{hidden: yes}). 
    Instead, the model exposes standardized, concatenated business attributes (combining natural codes with intuitive descriptions), streamlining consumption 
    for both human analysts and automated agents.
    \item \textbf{Optimizing join paths in analytical queries:} Although an Explore defines an extensive relational network to grant complete self-service flexibility, 
    Looker dynamically generates SQL containing only the joins required by the selected fields (\textbf{join pruning}). 
    Dashboard tiles are intentionally modeled to reference minimal join paths, avoiding unnecessary table traversals and reducing computational pressure on the database engine.
    \item \textbf{Establishing a curated semantic boundary:} LookML acts as a governed contract: attributes not explicitly defined or validated remain inaccessible to consuming tools. 
    Restricting exposure exclusively to certified dimensions protects downstream consumers from raw, uncurated schema changes and deprecated physical columns.
\end{itemize}

\subsection{Centralized Governance and the DRY Principle in Security Design}
A foundational engineering objective of formalizing business semantics in LookML is strict compliance with the \textit{Don't Repeat Yourself} (DRY) principle, 
which directly prevents code duplication and long-term maintenance overhead across enterprise analytics.

In conventional reporting architectures, enforcing data access segregation between distinct operational entities typically generates architectural anti-patterns. 
Technical teams are frequently forced to replicate entire models, SQL queries, or dashboard copies simply to hardcode facility-specific filtering criteria 
(e.g., maintaining cloned reports for each regional logistics deposit) or to strip out sensitive data columns for non-executive audiences. 
This duplication incurs severe operational risks: whenever an underlying business logic changes, the alteration must be manually propagated across every replicated asset, 
creating high maintenance costs, security vulnerabilities, and eventual metric drift.

Within the LookML framework, operational business definitions and data security boundaries are completely decoupled. 
The platform implements a unified \textit{Attribute-Based Access Control} (ABAC) architecture governed through centralized user attributes:
\begin{itemize}
    \item \textbf{Dynamic Row-Level Security (RLS) via \texttt{access\_filter}:} Rather than creating dedicated Explores or dashboards for different facilities, 
    row-level boundaries are enforced dynamically at query compilation time. Through Looker's \texttt{access\_filter} parameter, the engine maps an authenticated user's session 
    attributes directly to the target dimensional columns. When a user runs a query or loads a dashboard, Looker automatically injects the parameterized filtering predicates 
    into the generated SQL \texttt{WHERE} clause, ensuring strict data compartmentalization across the multi-site supply chain without duplicating a single line of modeling logic.
    \item \textbf{Granular Column-Level Security (CLS) via \texttt{required\_access\_grants}:} Sensitive metric and dimensional visibility is governed directly at the semantic 
    declaration level rather than by partitioning underlying database tables. 
    To safeguard confidential commercial or financial indicators without maintaining separate reporting views, LookML applies \texttt{required\_access\_grants} tied to specific 
    user attributes and permission sets. For instance, while gross material volumes are universally accessible to operational planners, sensitive measures tracking unit component 
    costs can be restricted to authorized roles. Users or automated agents lacking explicit entitlements are strictly prevented from querying the restricted measures or seeing them 
    exposed in the semantic metadata, achieving security by design within a single, centralized codebase.
\end{itemize}

\subsection{Implementation: Material Planning Fact and Master Views}
The operationalization of the Material Planning engine described in \Cref{chap:demandforecast} is implemented through a set of dedicated LookML views and explores. For editorial conciseness, the following listings present certified excerpts of the production LookML codebase, highlighting the primary fact aggregations and representative master attributes while omitting peripheral technical metadata.

The primary fact view, \texttt{f\_material\_planning}, defines the daily gross material requirements across forecast dates, finished items, logistics and production platforms, and packaging or ingredient components:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Definition for Material Planning Fact View (Partial Excerpt)}, label={lst:lookml_fact}]
view: f_material_planning {
  sql_table_name: `gsc-dp-mt-plan-sbx.material_planning_export.F_MATERIAL_PLANNING` ;;
  label: "Fabbisogno lordo materiali"

  dimension: primary_key {
    primary_key: yes
    type: string
    sql: concat(cast(${data_mp} as string), '-', cast(${art_id} as string), '-', 
                cast(${ptf_id} as string), '-', cast(${mat_id} as string), '-', 
                cast(${mat_um_id} as string)) ;;
    description: "Chiave primaria univoca: DATA_MP x ART_ID x PTF_ID x MAT_ID x MAT_UM_ID"
    hidden: yes
  }

  dimension_group: data_previsione {
    type: time
    label: "Data Previsione"
    timeframes: [raw, date, week, month, quarter, year]
    datatype: date
    convert_tz: no
    sql: ${data_mp} ;;
    description: "Data di previsione del fabbisogno lordo"
    synonyms: ["data di previsione", "data fabbisogno", "orizzonte temporale", "data pianificata"]
  }

  measure: fabbisogno_materiale {
    type: sum
    label: "Fabbisogno Materiale"
    sql: ${mat_qta} ;;
    description: "Fabbisogno lordo del materiale (imballo, etichetta o ingrediente) necessario a coprire la produzione pianificata, per deposito, data e unita di misura"
    value_format_name: decimal_0
    synonyms: ["fabbisogno lordo", "quantita materiale", "consumo previsto", "fabbisogno totale"]
    drill_fields: [dettaglio_fabbisogno*]
  }

  set: dettaglio_fabbisogno {
    fields: [
      materiale.tipo_materiale,
      materiale.materiale,
      data_previsione,
      fabbisogno_materiale,
      um_cod
    ]
  }
  
  measure: casse_articolo {
    type: sum
    label: "Casse Articolo"
    sql: ${art_casse} ;;
    description: "Casse di prodotto finito previste da cui derivano le quantita di materiale"
    value_format_name: decimal_0
    synonyms: ["volume casse", "casse previste", "casse equivalenti", "casse di prodotto finito", "volume in casse"]
    drill_fields: [dettaglio_casse*]
  }
  
  set: dettaglio_casse {
    fields: [
      prodotto.prodotto,
      data_previsione,
      casse_articolo
    ]
  }
}
\end{lstlisting}

In this fact view, the technical grain of the dataset is explicitly enforced through a composite \texttt{primary\_key} dimension, ensuring query uniqueness and preventing aggregation anomalies. Technical surrogate keys (\texttt{art\_id}, \texttt{mat\_id}, \texttt{ptf\_id}, \texttt{mat\_um\_id}) are encapsulated using \texttt{hidden: yes}, while the temporal attribute is declared via a structured \texttt{dimension\_group} providing automatic time-frame bucketing. Additive business measures—such as \texttt{fabbisogno\_materiale} and \texttt{casse\_articolo}—embed domain-specific definitions, numeric formatting rules, and contextual \texttt{drill\_fields} mappings.

Dimensional master views provide the descriptive attributes required to contextualize these fact aggregations. Across the semantic layer, master entities fall into two architectural categories: standard single-purpose lookups and polymorphic role-playing dimensions.

Standard master views maintain a direct one-to-one correspondence between the physical database table and the LookML view. A representative example is \texttt{l\_ptf}, which encapsulates logistics platforms, manufacturing plants, and distribution centers:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Definition for Standard Platform Master View (Partial Excerpt)}, label={lst:lookml_ptf}]
view: l_ptf {
  sql_table_name: `gsc-dp-mt-plan-sbx.material_planning_export.L_PTF` ;;
  label: "Piattaforma"

  dimension: ptf_id {
    primary_key: yes
    type: number
    sql: ${TABLE}.PTF_ID ;;
    hidden: yes
  }

  dimension: piattaforma_cod {
    type: string
    sql: ${TABLE}.PTF_COD ;;
    hidden: yes
  }

  dimension: piattaforma_des {
    type: string
    sql: ${TABLE}.PTF_DES ;;
    hidden: yes
  }

  dimension: piattaforma {
    type: string
    label: "Piattaforma"
    sql: concat(${piattaforma_cod}, ' - ',${piattaforma_des}) ;;
    description: "Codice e descrizione del deposito o piattaforma logistica"

\end{lstlisting}

As shown in \Cref{lst:lookml_ptf}, standard lookups clean the consumption surface: technical identifiers and fragmented code/description columns are kept internal, exposing a single concatenated business dimension (\texttt{piattaforma}) enriched with enterprise synonyms.

In contrast, the enterprise item registry, \texttt{l\_art\_jde}, represents a polymorphic dimension. In the corporate ERP system (JD Edwards), all physical inventory items—from finished commercial goods to packaging and raw materials—reside within a single unified table. 

Architecturally, modeling this registry could have followed two competing paradigms:
\begin{enumerate}
    \item \textbf{Dual View Anti-Pattern:} Authoring two distinct LookML view files (\texttt{prodotto.view.lkml} and \texttt{materiale.view.lkml}) pointing to the identical underlying physical table. While structurally intuitive, this approach directly violates the DRY principle. Maintaining duplicated codebases introduces severe maintenance risks: any upstream schema update or data type modification must be synchronized manually across multiple files, causing code drift and maintenance overhead.
    \item \textbf{Centralized Semantic View with Join-Level Role Playing (Implemented Architecture):} Consolidating all physical item attributes into a single authoritative LookML view (\texttt{l\_art\_jde}), while delegating operational specialization and field projection to the Explore model through aliased, role-playing joins.
\end{enumerate}

To enforce the DRY principle and ensure centralized maintainability, \texttt{l\_art\_jde} unifies the entire item schema within a single definition:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Master Articles View (Representative Excerpt)}, label={lst:lookml_master}]

    primary_key: yes
    type: number
    sql: ${TABLE}.ART_JDE_ID ;;
    hidden: yes
  }

  dimension: articolo_lcod {

    sql: ${TABLE}.ART_JDE_LCOD ;;
    hidden: yes
  }

  dimension: articolo_des {
    type: string
    sql: ${TABLE}.ART_JDE_DES ;;

  }

  dimension: materiale {

  }

  dimension: tipo_materiale {
    type: string

As documented in \Cref{lst:lookml_master}, \texttt{l\_art\_jde} defines the complete domain dictionary in a single source of truth. The operational role separation is then executed at the model configuration level (\Cref{lst:lookml_model}): the view is instantiated twice—aliased as \texttt{prodotto} and \texttt{materiale}—using explicit join-level field scoping (\texttt{fields: [...]}) to project only the relevant attributes into each respective business namespace.

\subsection{Model Definition: Relational Joins and Access Perimeter}
The relational orchestration of the Material Planning domain is codified within the LookML model file (\texttt{material\_planning.model.lkml}). The model specifies the active database connection, imports the view definitions, and defines the join topology centered around the primary fact view:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Model and Explore Configuration for Material Planning (Simplified Excerpt)}, label={lst:lookml_model}]
connection: "materialplanningbq"

include: "/views/*.view.lkml"

explore: material_planning {
  label: "Fabbisogno lordo materiali"

  access_filter: {
    field: l_ptf.piattaforma_cod
    user_attribute: piattaforma_autorizzata
  }

  join: prodotto {
    from: l_art_jde
    view_label: "Prodotto"
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.art_id} = ${prodotto.art_jde_id} ;;
    fields: [prodotto.prodotto, prodotto.articolo_neutro_cod]
  }

  join: materiale {
    from: l_art_jde
    view_label: "Materiale"
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.mat_id} = ${materiale.art_jde_id} ;;
    fields: [materiale.materiale, materiale.tipo_materiale]
  }

  join: l_ptf {
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.ptf_id} = ${l_ptf.ptf_id} ;;
  }

  join: l_um {
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.mat_um_id} = ${l_um.um_id} ;;
  }

  join: l_lin {
    type: inner
    relationship: many_to_one
    sql_on: ${prodotto.art_jde_lin_id} = ${l_lin.lin_id} ;;
  }

  join: l_fam {
    type: inner
    relationship: many_to_one
    sql_on: ${prodotto.art_jde_fam_id} = ${l_fam.fam_id} ;;
  }
}
\end{lstlisting}

As demonstrated in \Cref{lst:lookml_model}, the Explore configuration operationalizes the core architectural principles established across previous sections:
\begin{itemize}
    \item \textbf{Decoupled backend connection:} The top-level parameter \texttt{connection: "materialplanningbq"} targets the Google BigQuery analytical warehouse. Under the in-database compilation paradigm, altering this single parameter transitions the underlying engine dialect without modifying semantic field definitions or breaking downstream consumers.
    \item \textbf{Operationalized Row-Level Security:} The \texttt{access\_filter} block enforces the ABAC security framework defined earlier. User session attributes (\texttt{piattaforma\_autorizzata}) are automatically injected into the generated SQL \texttt{WHERE} clause at runtime, filtering platform-specific records dynamically across all queries without report duplication.
    \item \textbf{Role-playing dimension specialization:} The master table \texttt{l\_art\_jde} is instantiated twice: once as \texttt{prodotto} (finished commercial product driving demand) and once as \texttt{materiale} (raw material or packaging consumed). By restricting exposed attributes through the \texttt{fields} parameter, each joined entity projects only its contextually relevant dimensions, eliminating semantic collisions while preserving a centralized, DRY-compliant view definition.
    \item \textbf{Hierarchical snowflaking:} Upstream product classifications—specifically product lines (\texttt{l\_lin}) and item families (\texttt{l\_fam})—are joined directly to the \texttt{prodotto} alias, creating a normalized dimensional hierarchy while leaving the core fact table centered at the proper level of aggregation.
\end{itemize}

\subsection{Semantic Modeling for Self-Service Exploration and AI Enablement}
The systematic codification of business logic and contextual metadata within LookML serves a dual strategic objective: empowering the network of embedded \textbf{Data \& AI Champions} with governed self-service analytical capabilities, while simultaneously establishing an authoritative, deterministic semantic layer for autonomous cognitive agents.

\paragraph{Enabling Governed Self-Service Business Intelligence}
In conventional enterprise architectures, business units frequently encounter an operational bottleneck: every novel analytical inquiry requires technical ticketing requests to central data engineering teams. This structural friction encourages unmanaged data extraction into local spreadsheets, inevitably causing metric fragmentation, logic divergence, and corporate data silos.

To overcome this divide, the operating model formalized in \Cref{sec:organizational_transformation} introduces the network of \textbf{Data \& AI Champions}—domain specialists embedded directly within operational business units who bridge domain requirements with analytical execution. The LookML Semantic Layer serves as the primary technical enabler for these Champions, providing an intuitive, guardrailed interface that safely delegates analytical autonomy without compromising governance:

\begin{itemize}
    \item \textbf{Autonomous ad-hoc exploration via Symmetric Aggregates:} Within the unified \texttt{material\_planning} explore, the underlying physical complexity is translated into certified business dimensions and aggregated measures. By leveraging Looker's \textit{Symmetric Aggregates} engine—anchored to the composite \texttt{primary\_key} declared in the fact view—the platform mathematically eliminates fanout errors and Cartesian duplicates across multi-table joins. Champions can explore multidimensional cross-sections with mathematical confidence, fully protected against erroneous double-counting.
    \item \textbf{Diagnostic root-cause analysis via \texttt{drill\_fields}:} Beyond consuming pre-aggregated figures, Champions utilize interactive drill paths declared via \texttt{drill\_fields} on core metrics (such as \texttt{fabbisogno\_materiale} and \texttt{casse\_articolo}). Upon identifying anomalous demand variances, they can instantaneously deconstruct the aggregate volume into underlying material classifications, SKU codes, and daily scheduling buckets, diagnosing supply chain bottlenecks autonomously.
    \item \textbf{Decentralized dashboard curation and peer distribution:} Acting as analytical hubs within their units, Champions convert operational needs into curated analytical views (\textit{Looks}) and compose dynamic, cross-filtered dashboards for their peers. Because these operational assets are anchored directly to centralized LookML definitions, departmental dashboards inherit upstream logic updates automatically, relieving central engineering from routine reporting maintenance while preserving single-source metric integrity.
\end{itemize}

\paragraph{Enabling Grounded Generative AI Agents}
While human analysts and Champions interact with this semantic framework via visual exploration interfaces, the exact same declarative metadata acts as an auditable, deterministic API for autonomous Large Language Models (LLMs) and cognitive agents \cite{googlecloudlookerca2024}. 

Directly generating raw SQL from natural language queries (\textbf{Text-to-SQL}) presents well-documented enterprise risks, including syntax hallucinations, invalid table joins, and unconstrained computational costs. By positioning LookML as an intermediary semantic API, the cognitive agent targets curated semantic entities rather than raw relational tables, utilizing the underlying metadata for precise operational grounding:
\begin{itemize}
    \item \textbf{Domain vocabulary disambiguation via \texttt{synonyms}:} Natural language prompts rarely mirror physical database columns. The \texttt{synonyms} parameter maps colloquial supply chain jargon, operational acronyms (e.g., \textit{"PFL"}, \textit{"PFN"}, \textit{"fabbisogno lordo"}), and informal business expressions directly to validated LookML dimensions, allowing the agent to resolve user intent to deterministic schema fields.
    \item \textbf{Semantic grounding via \texttt{description}:} The \texttt{description} parameter defines the functional perimeter, source lineage, and aggregation logic of each measure. This declarative context supplies the LLM with unambiguous operational boundaries, preventing the model from misinterpreting calculated metrics or hallucinating arbitrary aggregation formulas.
    \item \textbf{Context window optimization via \texttt{hidden} attributes:} By suppressing internal surrogate identifiers, technical foreign keys, and administrative flags via \texttt{hidden: yes}, the semantic contract filters unnecessary noise from the agent's prompt context. The LLM processes only certified, business-actionable attributes, minimizing prompt token consumption and preventing unintended join pathways.
\end{itemize}

By encapsulating both calculation logic and semantic context directly within a version-controlled, auditable codebase, the architecture bridges human analytical workflows with autonomous computational intelligence. The concrete orchestration of this semantic layer with autonomous conversational agents, diagnostic reasoning loops, and dynamic dashboard routing is formally developed in \Cref{chap:conversational_agent}.

\section[Metadata Architecture Roadmap]{Governance Roadmap: Extending Lineage and Enterprise Knowledge via OpenMetadata}
\label{sec:openmetadata_roadmap}

Looker operates as the centralized semantic compiler and enforces metric governance at the analytical layer. However, achieving comprehensive visibility across the broader enterprise data lifecycle requires a dedicated metadata management platform. Currently, business definitions, dimensional attributes, and operational descriptions are codified directly within LookML files using parameters such as \texttt{description}, \texttt{label}, and \texttt{synonyms}. While this approach successfully establishes LookML as an executable ``Business Glossary as Code'', its access remains primarily restricted to analytics engineers and technical practitioners working within the version-controlled Git environment.

To decouple business glossary governance from technical codebases and automate end-to-end lineage across heterogeneous systems, the target architecture incorporates OpenMetadata as a future governance milestone. OpenMetadata is an open-source, schema-first metadata management platform built upon standard JSON schemas for data discovery, governance, and quality profiling. Within this planned evolution, OpenMetadata expands enterprise governance beyond the analytical boundary through three foundational capabilities:

\begin{enumerate}
    \item \textbf{Centralized, Low-Code Business Glossary:} Business definitions are transitioned from plain-text LookML parameters into an intuitive, low-code enterprise catalog accessible to non-technical stakeholders \cite{dama2024dmbok}. This interface empowers domain stewards across planning, supply chain, and commercial divisions to manage term ownership, certify metric definitions, and approve terminology changes collaboratively without submitting pull requests to a Git repository.
    \item \textbf{Automated End-to-End Data Lineage:} The platform establishes systematic traceability across the entire data lifecycle by connecting source catalogs directly to consuming assets. By tracing data assets from their operational origin in the on-premises Oracle database, through cloud landing zones and transformations in Google BigQuery, down to the semantic entities compiled by Looker, automated lineage enables engineering teams to perform proactive impact analysis. Practitioners can precisely determine which downstream Explores, operational dashboards, or predictive workloads would be affected prior to executing upstream schema migrations.
    \item \textbf{Enterprise Knowledge Graph Construction:} Enterprise metadata entities---including physical tables, pipeline orchestration schedules, semantic metric definitions, and access policies---are modeled as an interconnected knowledge graph \cite{hogan2021knowledge}. This unified structural topology provides deterministic insights into data provenance and operational quality, serving as an authoritative grounding fabric for autonomous AI workflows.
\end{enumerate}

In this target framework, OpenMetadata ingests metadata programmatically from Looker and underlying database instances via dedicated REST APIs, eliminating manual synchronization overhead. This architectural extension cleanly decouples analytical query compilation (orchestrated in-database by Looker across Oracle and BigQuery) from enterprise-wide metadata governance, completing the structural transition toward federated Data Products.

\bigskip
The technical architecture deployed at Amadori S.p.A. provides a resilient migration bridge, facilitating a secure and phased transition from legacy on-premises transactional systems toward the analytical scalability of Google BigQuery. By establishing Looker as the in-database Semantic Layer, the enterprise insulates operational reporting from physical storage cutovers, enforces the DRY principle across its metric catalog, guarantees granular Attribute-Based Access Control, and encapsulates complex supply chain dynamics within certified LookML models. With the foundational storage migration, relational modeling patterns, and metadata governance roadmap established, the subsequent chapter examines how this unified semantic layer enables autonomous conversational analytics through Gemini in Looker.
