\section[Backend Infrastructure]{Backend infrastructure and Data Platform architecture}
\label{sec:backend_infrastructure}

To operationalize the domain-oriented Data Product model and support interactive analytical workloads within Amadori S.p.A.,
the enterprise data architecture is undergoing a gradual transition from an on-premises relational infrastructure toward a cloud-native platform.

The baseline enterprise environment relies primarily on an on-premises Oracle database, which has historically served as the operational transaction
repository and the default target for analytical queries. To overcome the computational constraints of on-premises hardware and reduce
contention between transactional processing and resource-intensive analytics, the target architecture introduces Google BigQuery as the enterprise cloud data warehouse.
BigQuery provides a serverless environment based on distributed compute and columnar storage, well suited to analytical queries over large historical datasets.

Rather than an abrupt cutover, the transition follows a phased strategy.
In a first production phase, Looker queries the operational Oracle database directly.
As data models, historical partitions, and ETL routines are progressively refactored and validated, tables are transferred to Google BigQuery,
and both environments remain active concurrently during the transitional period.

The Material Planning domain illustrates how this strategy is applied in practice. The material requirements calculation described in \Cref{chap:demandforecast}
runs as a nightly batch job on Oracle and populates the core fact table, \texttt{F\_\allowbreak MATERIAL\_\allowbreak PLANNING}.
Since the direct connection between Looker and Oracle was not yet available during the development of this work, the semantic model was prototyped against a
BigQuery sandbox project (\texttt{material\_\allowbreak planning\_\allowbreak export}), into which the Oracle output tables were exported manually.
This setup made it possible to design and validate the LookML model and the conversational agent on real data, but it is not sustainable as an operating solution,
since it relies on repeated manual loads. Once the Looker--Oracle connection is in place, the model will query Oracle directly;
at a later stage, when the pipeline itself is migrated, it will be pointed to the production BigQuery tables.

\section[The Semantic Layer with Looker and LookML]{Formalizing business data:\\ the Semantic Layer with Looker and LookML}
\label{sec:looker_lookml}

To operationalize the conceptual definitions established by the enterprise ontology and provide an auditable single source of truth across analytical processes, 
the architecture implements Looker and its declarative modeling language, LookML. In this stack, Looker acts not merely as a visualization layer, 
but as the execution engine of the enterprise Semantic Layer \cite{patel2023comparative}.
Operating on an in-database query paradigm, the platform does not extract data into its own storage: it compiles user requests, dashboards,
and API calls into SQL queries that are executed by the underlying database at runtime \cite{gartner2021magic}.

This abstraction is what makes the phased migration described in \Cref{sec:backend_infrastructure} manageable.
Because semantic definitions are isolated from the physical database, the same LookML model can move from the BigQuery sandbox to Oracle, and later to production BigQuery,
by changing the model connection and adapting the dialect-specific SQL fragments (e.g., table references and string functions).
The business entities and measures exposed to users, reports, and AI interfaces remain unchanged, so downstream consumers are largely insulated from the storage transition.

\subsection{Architectural best practices and performance optimization}
Designing a Semantic Layer requires balancing analytical flexibility with computational efficiency.
When modeling the Material Planning domain in LookML, the following design guidelines were adopted to limit query cost and maintenance effort \cite{googlecloudlookerbp2024};
their concrete application is shown in the listings of the following subsections:
\begin{itemize}
    \item \textbf{Pushing transformations upstream:} Complex business logic, recursive allocations, and rolling aggregations are computed
    during database batch processing rather than inside LookML.
    Looker is used for dimensional aggregation, filtering, and metric definition, avoiding expensive row-level computations at query time.
    \item \textbf{Denormalization of frequently filtered attributes:} While normalization minimizes redundancy in transactional (OLTP) systems,
    analytical workloads benefit from flatter structures. Frequently joined descriptive attributes are denormalized,
    reducing join depth on large fact tables.
    \item \textbf{Exposing business identifiers instead of surrogate keys:} Technical keys used for joins are kept internal,
    and the model exposes business attributes that combine natural codes with readable descriptions.
    \item \textbf{Join pruning:} Although an Explore defines a wide network of joins to support self-service analysis,
    Looker generates SQL containing only the joins required by the selected fields, so a broad Explore does not imply expensive queries.
    \item \textbf{A curated semantic boundary:} LookML acts as a contract: attributes that are not explicitly modeled are not accessible to consuming tools,
    which protects downstream consumers from uncurated schema changes and deprecated physical columns.
\end{itemize}

\subsection{Centralized governance and the DRY principle in Security Design}
A central objective of formalizing business semantics in LookML is compliance with the \textit{Don't Repeat Yourself} (DRY) principle:
each definition is written once and reused, avoiding duplicated code and the maintenance effort it entails.

Access control is a typical source of duplication in conventional reporting architectures.
Technical teams are often forced to replicate models, SQL queries, or dashboards simply to hardcode facility-specific filters
(e.g., one copy of a report for each logistics deposit) or to remove sensitive columns for some audiences.
Every change in the underlying logic must then be propagated manually to each copy, increasing maintenance costs and the risk of inconsistent metrics.

In LookML, business definitions and access rules are kept separate, and access is governed through centralized user attributes,
following an \textit{Attribute-Based Access Control} (ABAC) approach:
\begin{itemize}
    \item \textbf{Row-Level Security (RLS) via \texttt{access\_filter}:} Instead of creating dedicated Explores or dashboards for each facility,
    row-level restrictions are applied at query compilation time. The \texttt{access\_filter} parameter maps a user attribute to a model dimension,
    and Looker adds the corresponding predicate to the \texttt{WHERE} clause of every generated query.
    A single model therefore serves all sites, each user seeing only the platforms they are authorized for (see \Cref{lst:lookml_model}).
    \item \textbf{Column-Level Security (CLS) via \texttt{required\_access\_grants}:} The same principle can be extended to columns.
    By attaching \texttt{required\_access\_grants} to specific fields, sensitive measures could be
    restricted to authorized roles, while gross material volumes remain available to all planners.
    Users or agents without the required grant would neither query nor see these fields, without the need for separate reporting views.
\end{itemize}

\subsection{Implementation: Material Planning fact and master views}
The operationalization of the Material Planning engine described in \Cref{chap:demandforecast} is implemented through a set of dedicated LookML views and explores. For editorial conciseness, the following listings present certified excerpts of the production LookML codebase, highlighting the primary fact aggregations and representative master attributes while omitting peripheral technical metadata.

The primary fact view, \texttt{f\_material\_planning}, defines the daily gross material requirements across forecast dates, finished items, logistics and production platforms, and packaging or ingredient components:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Definition for Material Planning Fact View (Partial Excerpt)}, label={lst:lookml_fact}]

  sql_table_name: `gsc-dp-mt-plan-sbx.material_planning_export.F_MATERIAL_PLANNING` ;;
  label: "Fabbisogno lordo materiali"

  dimension: primary_key {
    primary_key: yes
    type: string
    sql: concat(cast(${data_mp} as string), '-', cast(${art_id} as string), '-', 
                cast(${ptf_id} as string), '-', cast(${mat_id} as string), '-', 
                cast(${mat_um_id} as string)) ;;
    description: "Chiave primaria univoca: DATA_MP x ART_ID x PTF_ID x MAT_ID x MAT_UM_ID"
    hidden: yes
  }

  dimension_group: data_previsione {

  }

    value_format_name: decimal_0

    drill_fields: [dettaglio_fabbisogno*]
  }

  set: dettaglio_fabbisogno {

      materiale.tipo_materiale,

  }

\end{lstlisting}

In this fact view, the technical grain of the dataset is explicitly enforced through a composite \texttt{primary\_key} dimension, ensuring query uniqueness and preventing aggregation anomalies. Technical surrogate keys (\texttt{art\_id}, \texttt{mat\_id}, \texttt{ptf\_id}, \texttt{mat\_um\_id}) 
are encapsulated using \texttt{hidden: yes}, while the temporal attribute is declared via a structured \texttt{dimension\_group} providing automatic time-frame bucketing. 
Additive business measures—such as \texttt{fabbisogno\_materiale}—embed domain-specific definitions, numeric formatting rules, and contextual \texttt{drill\_fields} mappings.

Dimensional master views provide the descriptive attributes required to contextualize these fact aggregations. Across the semantic layer, master entities fall into two architectural categories: standard single-purpose lookups and polymorphic role-playing dimensions.

Standard master views maintain a direct one-to-one correspondence between the physical database table and the LookML view. A representative example is \texttt{l\_ptf}, which encapsulates logistics platforms, manufacturing plants, and distribution centers:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Definition for Standard Platform Master View (Partial Excerpt)}, label={lst:lookml_ptf}]
view: l_ptf {
  sql_table_name: `gsc-dp-mt-plan-sbx.material_planning_export.L_PTF` ;;
  label: "Piattaforma"

  dimension: ptf_id {
    primary_key: yes
    type: number
    sql: ${TABLE}.PTF_ID ;;
    hidden: yes
  }

  dimension: piattaforma_cod {

  }

As shown in \Cref{lst:lookml_ptf}, standard lookups clean the consumption surface: technical identifiers and fragmented code/description columns are kept internal, exposing a single concatenated business dimension (\texttt{piattaforma}) enriched with enterprise synonyms.

In contrast, the enterprise item registry, \texttt{l\_art\_jde}, represents a polymorphic dimension. In the corporate ERP system (JD Edwards), all physical inventory items—from finished commercial goods to packaging and raw materials—reside within a single unified table. 

Architecturally, modeling this registry could have followed two competing paradigms:
\begin{enumerate}
    \item \textbf{Dual View Anti-Pattern:} Authoring two distinct LookML view files (\texttt{prodotto.view.lkml} and \texttt{materiale.view.lkml}) pointing to the identical underlying physical table. While intuitive, this approach violates the DRY principle: any upstream schema or data type change must be synchronized manually across multiple files, with a risk of divergence over time.
    \item \textbf{Centralized Semantic View with Join-Level Role Playing (Implemented Architecture):} Consolidating all physical item attributes into a single authoritative LookML view (\texttt{l\_art\_jde}), while delegating operational specialization and field projection to the Explore model through aliased, role-playing joins.
\end{enumerate}

Following the second approach, \texttt{l\_art\_jde} unifies the entire item schema within a single definition:

As documented in \Cref{lst:lookml_master}, \texttt{l\_art\_jde} defines the complete domain dictionary in a single source of truth. The operational role separation is then executed at the model configuration level (\Cref{lst:lookml_model}): the view is instantiated twice—aliased as \texttt{prodotto} and \texttt{materiale}—using explicit join-level field scoping (\texttt{fields: [...]}) to project only the relevant attributes into each respective business namespace.

\subsection{Model definition: relational joins and access perimeter}
The relational orchestration of the Material Planning domain is codified within the LookML model file (\texttt{material\_planning.model.lkml}). The model specifies the active database connection, imports the view definitions, and defines the join topology centered around the primary fact view:

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={LookML Model and Explore Configuration for Material Planning (Simplified Excerpt)}, label={lst:lookml_model}]
connection: "materialplanningbq"

include: "/views/*.view.lkml"

explore: material_planning {
  label: "Fabbisogno lordo materiali"

  access_filter: {
    field: l_ptf.piattaforma_cod
    user_attribute: piattaforma_autorizzata
  }

  join: prodotto {
    from: l_art_jde
    view_label: "Prodotto"
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.art_id} = ${prodotto.art_jde_id} ;;
    fields: [prodotto.prodotto, prodotto.articolo_neutro_cod]
  }

  join: materiale {
    from: l_art_jde
    view_label: "Materiale"
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.mat_id} = ${materiale.art_jde_id} ;;
    fields: [materiale.materiale, materiale.tipo_materiale]
  }

  join: l_ptf {
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.ptf_id} = ${l_ptf.ptf_id} ;;
  }

  join: l_um {
    type: inner
    relationship: many_to_one
    sql_on: ${f_material_planning.mat_um_id} = ${l_um.um_id} ;;
  }

  join: l_lin {
    type: inner
    relationship: many_to_one
    sql_on: ${prodotto.art_jde_lin_id} = ${l_lin.lin_id} ;;
  }

  join: l_fam {
    type: inner
    relationship: many_to_one
    sql_on: ${prodotto.art_jde_fam_id} = ${l_fam.fam_id} ;;
  }
}
\end{lstlisting}

\Cref{lst:lookml_model} shows how the principles introduced in the previous subsections are applied in the Explore configuration:
\begin{itemize}
    \item \textbf{Backend connection:} The parameter \texttt{connection: "materialplanningbq"} currently points to the BigQuery sandbox described in \Cref{sec:backend_infrastructure}. Moving the model to Oracle, and later to production BigQuery, mainly requires changing this parameter and adapting dialect-specific SQL, while field definitions remain unchanged.
    \item \textbf{Row-Level Security:} The \texttt{access\_filter} block binds the user attribute \texttt{piattaforma\_autorizzata} to the platform code, so every query is automatically restricted to the platforms the user is authorized for.
    \item \textbf{Role-playing dimensions:} The master table \texttt{l\_art\_jde} is joined twice, as \texttt{prodotto} (the finished product driving demand) and as \texttt{materiale} (the raw material or packaging consumed). The join-level \texttt{fields} parameter projects only the relevant attributes into each namespace, avoiding ambiguous field names while keeping a single view definition.
    \item \textbf{Hierarchical snowflaking:} Product lines (\texttt{l\_lin}) and families (\texttt{l\_fam}) are joined to the \texttt{prodotto} alias rather than to the fact table, forming a dimensional hierarchy while the fact table keeps its original grain.
\end{itemize}

\paragraph{Known limitation and planned improvement: units of measure}
The current model leaves one aggregation risk open. The measure \texttt{fabbisogno\_materiale} is a sum, but material requirements are expressed in different units: kilograms, square or linear meters, and pieces. Summing quantities across units produces a number with no physical meaning. At present, the unit of measure is exposed as an ordinary filter, as shown in \Cref{fig:looker_selfservice,fig:looker_look}: it is up to the user, or to the author of a Look, to restrict each query to a single unit, and nothing in the model prevents several units from being selected or the filter from being removed.

A planned evolution moves this rule into the model itself, as sketched in \Cref{lst:lookml_um_param}. The unit would be selected through a LookML \texttt{parameter}, which, unlike an ordinary filter, accepts exactly one value from a fixed list. The \texttt{sql\_always\_where} clause would inject the selected unit into the \texttt{WHERE} clause of every query, while \texttt{always\_filter} would keep the selector visible, with kilograms as the default. Every query on the Explore would thus refer to a single unit of measure, and the rule would be enforced once in the model rather than left to the attention of each user or Look. The trade-off is that comparing quantities expressed in different units would require separate queries.

\begin{lstlisting}[language=SQL, basicstyle=\footnotesize\ttfamily, caption={Proposed LookML Configuration for Single Unit-of-Measure Selection (Not Yet Implemented)}, label={lst:lookml_um_param}]
# view l_um: single-choice selector
parameter: um_selezionata {
  type: string
  label: "Unita di misura"
  allowed_value: { value: "KG - Chilogrammi" }
  allowed_value: { value: "MQ - Metro quadrato" }
  allowed_value: { value: "MT - Metro lineare" }
  allowed_value: { value: "NR - Numero" }
  default_value: "KG - Chilogrammi"
}

# explore material_planning: mandatory constraint
always_filter: {
  filters: [l_um.um_selezionata: "KG - Chilogrammi"]
}
sql_always_where: ${l_um.um} = {% parameter l_um.um_selezionata %} ;;
\end{lstlisting}

Expanding a namespace, such as \textit{Materiale} in the figure, reveals only the few dimensions projected through the join-level \texttt{fields} parameter. The interface is thus the visible counterpart of the curated semantic boundary: the whole Material Planning domain is reduced to a compact catalog of certified fields.

\subsection{Development lifecycle and version control}
\label{subsec:lookml_lifecycle}
Because the semantic model is code, its evolution follows a software development lifecycle rather than ad-hoc changes to reports. The LookML project is connected to a Git repository, and Looker separates two environments:
\begin{itemize}
    \item \textbf{Development Mode:} each developer works on a personal Git branch and sees the effect of their changes in the Explore without affecting other users.
    \item \textbf{Production Mode:} all business users, Looks, dashboards, and the conversational agent query the version of the model on the production branch.
\end{itemize}

Moving a change from development to production follows a controlled sequence. Before committing, the \textit{LookML Validator} checks the model for syntax errors, references to undefined fields, and invalid join definitions, while the \textit{Content Validator} identifies saved Looks and dashboards that would break because of renamed or removed fields. Changes are then committed to the developer's branch and proposed through a pull request; only after review and approval they are merged into the production branch and deployed.
This workflow makes every change to a metric definition traceable (who changed it, when, and why) and reversible, and it is what makes the description of LookML as an auditable, version-controlled codebase concrete. It also connects the semantic layer to the organizational model of \Cref{sec:organizational_transformation}: Champions can propose changes to definitions, but these reach production only through a reviewed and validated process.

\subsection{Semantic modeling for self-service exploration and AI enablement}
The codification of business logic and contextual metadata in LookML serves two purposes: giving the Data \& AI Champions governed self-service analytical capabilities, and providing a reliable semantic layer for conversational agents.

\paragraph{Enabling governed self-service Business Intelligence}
In conventional enterprise architectures, every new analytical question typically requires a request to the central data team. This friction encourages unmanaged data extraction into local spreadsheets, leading to divergent metric definitions and data silos.

To address this, the operating model described in \Cref{sec:organizational_transformation} introduces the \textbf{Data \& AI Champions}, domain specialists embedded in the business units who connect operational requirements with analytical execution. The LookML Semantic Layer is their main technical enabler, offering an interface that delegates analytical autonomy within governed boundaries:

\begin{itemize}
    \item \textbf{Ad-hoc exploration with consistent aggregation:} Within the \\ \texttt{material\_planning} Explore, the physical data structure is presented as certified business dimensions and measures. In the current model all joins are \texttt{many\_to\_one} from the fact table, so fact measures are not duplicated by joins. Moreover, every view declares a primary key. This has no effect on the current measures, but if measures were later added to a joined view (e.g., a warehouse capacity in \texttt{l\_ptf}), Looker's \textit{Symmetric Aggregates} would use these keys to count each platform only once, instead of once per joined fact row. Champions can therefore combine dimensions freely without having to reason about join cardinalities.
    \item \textbf{Root-cause analysis via \texttt{drill\_fields}:} Core measures such as \\ \texttt{fabbisogno\_materiale} and \texttt{casse\_articolo} declare drill paths. When a Champion notices an anomalous value, a click decomposes it into material types, items, and dates, supporting a first diagnosis without technical support.
    \item \textbf{Reusable Looks as building blocks for dashboards:} Champions convert recurring operational questions into saved, named analytical views (\textit{Looks}), which are then assembled into dashboards for their colleagues. Since both are built on the central LookML definitions, they automatically reflect upstream logic changes, reducing the reporting maintenance carried by the central team.
\end{itemize}

\Cref{fig:looker_selfservice} illustrates a typical ad-hoc inquiry performed by a Champion without writing any SQL. Starting from the Explore, the user selects the \textit{Fabbisogno Materiale} measure, breaks it down by product line (\textit{Linea}) and forecast quarter, and restricts the scope through three filters: a single logistics platform, the \textit{Ingrediente} material type, and kilograms as unit of measure. Looker compiles these selections into a single SQL statement, translating each filter into a predicate of the \texttt{WHERE} clause (alongside any \texttt{access\_filter} bound to the user's attributes) and including only the joins required by the selected fields. The result is rendered as a set of donut charts, one per quarter, showing how ingredient requirements are distributed across product lines over the planning horizon.

Once validated, such an exploration is not left as a one-off query but saved as a \textit{Look}, as shown in \Cref{fig:looker_look}. A Look is a named, persistent analytical asset that stores the selected fields, filters, and visualization settings, and is published in a shared folder where business users consume it in read-only mode. Users can still adjust the exposed filters (e.g., platform, material type, or unit of measure), whose suggested values are populated directly from the LookML model, without being able to alter the underlying query definition. For this reason the Look is deliberately given a generic title: the same asset answers the question for ingredients in kilograms as well as for packaging in linear meters, simply by changing the filter values.

Creating Looks before dashboards is the recommended practice in the adopted operating model. Each Look encapsulates a single, validated analytical question and becomes a reusable building block: the same Look can be embedded as a tile in multiple dashboards, shared via direct link, scheduled for periodic delivery, or used as a starting point for further exploration. Dashboards are therefore composed of Looks rather than of ad-hoc tiles built from scratch, so a correction or refinement applied once to a Look propagates to every dashboard that references it. This mirrors, at the consumption layer, the DRY principle already enforced in the LookML model: the metric is defined once in the semantic layer, the analytical question is defined once in a Look, and dashboards only orchestrate their composition and shared filters.

\paragraph{Enabling grounded generative AI Agents}
The same metadata that guides human users through the Explore also serves as the interface for Large Language Model (LLM) agents \cite{googlecloudlookerca2024}. As discussed in \Cref{sec:semantic_layer}, letting an agent query a curated semantic model instead of generating raw SQL (\textit{Text-to-SQL}) reduces the risk of invalid joins and incorrect calculations. In the Material Planning model, three LookML parameters contribute directly to this grounding:
\begin{itemize}
    \item \textbf{\texttt{synonyms} for vocabulary disambiguation:} Users rarely phrase questions with database column names. Synonyms map colloquial supply chain terms and acronyms (e.g., \textit{PFL}, \textit{PFN}, \textit{fabbisogno lordo}) to the corresponding LookML fields, helping the agent resolve user intent.
    \item \textbf{\texttt{description} for semantic grounding:} Descriptions state the meaning, scope, and aggregation logic of each field, giving the model the context needed to choose the right measure instead of improvising a calculation.
    \item \textbf{\texttt{hidden} for a smaller search space:} Fields hidden from users are also excluded from the agent's context, so the model only reasons over business-relevant attributes.
\end{itemize}

How these elements are used by the conversational agent, and how their effect was evaluated, is discussed in \Cref{chap:conversational_agent}.

\section[Metadata Architecture Roadmap]{Governance roadmap: extending lineage and enterprise knowledge via OpenMetadata}
\label{sec:openmetadata_roadmap}

Looker operates as the centralized semantic compiler and enforces metric governance at the analytical layer. However, achieving comprehensive visibility across the broader enterprise data lifecycle requires a dedicated metadata management platform. Currently, business definitions, dimensional attributes, and operational descriptions are codified directly within LookML files using parameters such as \texttt{description}, \texttt{label}, and \texttt{synonyms}. While this approach successfully establishes LookML as an executable ``Business Glossary as Code'', its access remains primarily restricted to analytics engineers and technical practitioners working within the version-controlled Git environment.

To decouple business glossary governance from technical codebases and automate end-to-end lineage across heterogeneous systems, the target architecture incorporates OpenMetadata as a future governance milestone. OpenMetadata is an open-source, schema-first metadata management platform built upon standard JSON schemas for data discovery, governance, and quality profiling. Within this planned evolution, OpenMetadata expands enterprise governance beyond the analytical boundary through three foundational capabilities:

\begin{enumerate}
    \item \textbf{Centralized, Low-Code Business Glossary:} Business definitions are transitioned from plain-text LookML parameters into an intuitive, low-code enterprise catalog accessible to non-technical stakeholders \cite{dama2024dmbok}. This interface empowers domain stewards across planning, supply chain, and commercial divisions to manage term ownership, certify metric definitions, and approve terminology changes collaboratively without submitting pull requests to a Git repository.
    \item \textbf{Automated End-to-End Data Lineage:} The platform establishes systematic traceability across the entire data lifecycle by connecting source catalogs directly to consuming assets. By tracing data assets from their operational origin in the on-premises Oracle database, through cloud landing zones and transformations in Google BigQuery, down to the semantic entities compiled by Looker, automated lineage enables engineering teams to perform proactive impact analysis. Practitioners can determine which downstream Explores, operational dashboards, or predictive workloads would be affected prior to executing upstream schema migrations.
    \item \textbf{Enterprise Knowledge Graph Construction:} Enterprise metadata entities---including physical tables, pipeline orchestration schedules, semantic metric definitions, and access policies---are modeled as an interconnected knowledge graph \cite{hogan2021knowledge}. This structure makes data provenance and quality explicit and can serve as an additional grounding source for AI workflows.
\end{enumerate}

In this target framework, OpenMetadata ingests metadata from Looker and the underlying databases through their APIs, reducing manual synchronization. This separates analytical query compilation, performed in-database by Looker on Oracle and BigQuery, from enterprise-wide metadata governance, a further step toward federated Data Products.

\bigskip
In summary, the technical architecture adopted at Amadori S.p.A. supports a phased transition from on-premises Oracle toward Google BigQuery, with Looker acting as an in-database Semantic Layer that shields reports and AI interfaces from changes in the underlying storage. The LookML model centralizes metric definitions according to the DRY principle, enforces platform-level access through user attributes, and exposes the Material Planning domain as a curated set of business fields. The next chapter examines how this semantic layer is used by conversational agents through Gemini in Looker.
